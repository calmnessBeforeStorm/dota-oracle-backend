# Спецификация: система прогнозирования исходов профессиональных матчей Dota 2

**Версия:** 0.1 (черновик)
**Дата:** 26 августа 2026
**Статус:** к обсуждению

---

## 1. Цель и границы проекта

### 1.1 Что делаем

Веб-сервис, который в реальном времени оценивает вероятность победы каждой из команд в **идущих прямо сейчас** матчах Dota 2 на турнирах Tier 1, и предоставляет турнирный календарь в стиле Liquipedia (текущие / предстоящие / прошедшие турниры).

### 1.2 Что НЕ делаем (явно вне скоупа v1)

- Прогнозы на паб-матчи и матчи вне про-сцены.
- Букмекерская функциональность, приём ставок, сравнение с коэффициентами.
- Прогноз конкретных статистических исходов (тотал килов, длительность, first blood) — только исход карты.
- Прогноз победителя турнира целиком.

### 1.3 Ключевое разделение задач

Проект содержит **две разные ML-задачи**, которые нельзя смешивать:

| | Pre-match модель | **Live модель (основная)** |
|---|---|---|
| Когда работает | до старта карты | каждые 20–30 сек во время игры |
| Вход | сила команд, форма, ростеры, патч | состояние игры + prior от pre-match |
| Ожидаемое качество | 60–65% acc, log loss ≈ 0.63 | 65–70% на 10-й мин, 78–83% на 20-й, 88%+ на 30-й |
| Роль в v1 | вспомогательная (даёт prior) | **основной продукт** |

### 1.4 Глоссарий

- **Карта (map / game)** — одна партия Dota 2. Единица прогноза.
- **Серия (series)** — Bo1/**Bo2**/Bo3/Bo5 между двумя командами. Состоит из карт.
- **Ничья в серии** — исход 1–1 в Bo2. Возможен **только на уровне серии**; отдельная карта в Dota 2 ничьёй закончиться не может, победитель есть всегда.
- **Tier 1** — уровень турнира по классификации Liquipedia (см. §3).
- **Снапшот** — состояние игры в конкретную минуту. Строка обучающей выборки live-модели.
- **Parsed match** — матч, для которого OpenDota распарсил реплей (есть поминутные ряды).

### 2.2 Источник A — OpenDota API

**База:** `https://api.opendota.com/api`

#### A1. Список про-матчей — `GET /proMatches`

Пагинация назад по всей истории через `?less_than_match_id={id}`, ~100 матчей за вызов.

Поля: `match_id`, `start_time`, `duration`, `leagueid`, `league_name`, `radiant_team_id`, `radiant_name`, `dire_team_id`, `dire_name`, `radiant_win`, `radiant_score`, `dire_score`, `series_id`, `series_type`.

`series_id` + `series_type` критичны — по ним склеиваются карты в серии. Наблюдаемые значения `series_type`: `0` = Bo1, `1` = Bo3, `2` = Bo5.

> **Важно: Bo2 в `series_type` не представлен.** Поле приходит из Valve, и для Bo2-серий обычно проставляется `0`, а две карты могут как разделять `series_id`, так и не разделять. Автоматически отличить Bo2 от двух независимых Bo1 по данным Steam/OpenDota **невозможно**. Формат серии определяется по стадии турнира из Liquipedia (§5.5), а `series_type` используется только как подсказка.

#### A2. Детали матча — `GET /matches/{match_id}`

Один вызов на матч. **Главный источник датасета.**

Матч-уровень:
- `radiant_win` — целевая переменная
- `duration`, `start_time`, `leagueid`, `game_mode`, `lobby_type`
- `tower_status_radiant` / `tower_status_dire`, `barracks_status_radiant` / `barracks_status_dire` — битовые маски строений
- `picks_bans[]` — полный драфт с порядком (`is_pick`, `hero_id`, `team`, `order`)
- `objectives[]` — лог событий с таймстемпами (башни, Рошан, аегис, тир-килы)
- `teamfights[]` — тимфайты с уроном и золотом
- `version` — **если `null`, матч не распарсен**, поминутных рядов не будет

Поминутные ряды (только для parsed):
- `radiant_gold_adv[]` — преимущество Radiant по золоту, индекс = минута
- `radiant_xp_adv[]` — то же по опыту

Игроки — массив `players[]`, по одному объекту на игрока:
- `account_id` — **ключ для рейтингов игроков и детекта стендинов**
- `hero_id`, `player_slot` (< 128 = Radiant), `lane_role`, `is_roaming`
- `kills`, `deaths`, `assists`, `last_hits`, `denies`, `net_worth`, `level`
- `gold_per_min`, `xp_per_min`, `hero_damage`, `tower_damage`, `hero_healing`
- `gold_t[]`, `xp_t[]`, `lh_t[]`, `dn_t[]` — **поминутные ряды по каждому игроку**
- `item_0..item_5`, `purchase_log[]`, `kills_log[]`, `obs_placed`, `sen_placed`
- `leaver_status` — фильтр дисконнектов

Вложенные `radiant_team`, `dire_team`, `league` — справочные данные.

#### A3. Справочники

- `GET /leagues` — все лиги, поле `tier` со значениями `premium` / `professional` / `amateur`. Дешёвый прокси для тира до полноценного маппинга на Liquipedia.
- `GET /teams`, `GET /teams/{id}/players` — команды и составы
- `GET /proPlayers` — про-игроки с `account_id`, `team_id`, `name`, `fantasy_role`
- `GET /constants/heroes`, `/constants/items`, `/constants/patch` — константы (можно брать из репозитория `odota/dotaconstants` без расхода квоты)

#### A4. Бюджет квоты

| Объём | Вызовов | Время при 60 req/min |
|---|---|---|
| 1 год про-матчей (~20–25k карт) | ~25 000 | ~7 часов |
| 3 года | ~75 000 | ~21 час |

Год истории укладывается в половину месячной бесплатной квоты. Три года — три месяца фонового скачивания, либо ускоряется бэкфиллом через STRATZ (§2.3).

> **Измерено 27.08.2026 на реальном бэкфилле (5300 матчей, 128 дней истории, 37 лиг):
> 41,4 матча в сутки, то есть ≈ 15 100 карт в год** — примерно на треть меньше оценки выше.
> Пересчёт бюджета:
>
> | Объём | Список `/proMatches` | Детали `/matches/{id}` | Время деталей |
> |---|---|---|---|
> | 1 год | ~151 вызов (~3 мин) | ~15 100 | ~15,3 часа |
> | 3 года | ~453 вызова (~8 мин) | ~45 300 | ~46 часов |
>
> **Скорость деталей упирается не в rate limit, а в время ответа.** Замерено: 150 карт за
> 9 мин 04 сек, то есть ~16,5 карт в минуту, а не 60 — полный payload матча большой, и
> OpenDota собирает его ~3,5 сек. Планировать надо по этой цифре.
>
> Практический вывод: **три года истории укладываются в одну месячную бесплатную квоту
> OpenDota (50 000) без STRATZ**, но это ~46 часов фоновой закачки, а не 12. Открытый
> вопрос §14.1 «2 года или 4+» упирается не в квоту, а в это время и в дрейф меты.
> Скачивание списка матчей практически бесплатно — дорого только вытягивание деталей,
> по одному вызову на карту. Именно здесь STRATZ (§2.3) окупается: он отдаёт до сотни
> матчей одним запросом.

**Оговорка:** эндпоинт `/explorer` (произвольный SQL по базе OpenDota) периодически ограничивали для анонимных пользователей из-за нагрузки. Удобен для разведки, но пайплайн на нём строить нельзя. Проверить доступность на момент старта.

### 2.3 Источник B — STRATZ GraphQL

**База:** `https://api.stratz.com/graphql`, авторизация Bearer-токеном (бесплатный после логина на stratz.com).

**Роль (пересмотрена 27.08.2026): основной источник поминутных рядов**, а не ускоритель бэкфилла. Две причины, обе измерены — подробности в `docs/superpowers/specs/2026-08-27-stratz-adapter-design.md`:

1. **Лимит.** У OpenDota первым бьёт суточный лимит (~700 карт), у STRATZ — часовой (~2000 запросов). Те же 700 карт занимают минуты, а не сутки.
2. **Величина.** Поминутный ряд OpenDota (`gold_t`, `radiant_gold_adv`) — это **накопленное добытое золото**. Ряд STRATZ (`networthPerMinute`, `radiantNetworthLeads`) — это **net worth**, ровно то, что отдаёт live-табло `GetLiveLeagueGames`. Обучение на OpenDota означало train/serve skew на самом сильном признаке.

Полезные корневые запросы:
- `match(id:)` — детали одного матча, **основной рабочий запрос**
- `league(id:)` → `matches(request: {take, skip})` — матчи турнира пачкой
- `team(teamId:)` → `matches`, `members`
- `player(steamAccountId:)` → история, герои
- `live` — идущие матчи (резервный канал для §2.4)

Набор полей, из которого строятся снапшоты: `id`, `didRadiantWin`, `durationSeconds`, `parsedDateTime`, `radiantNetworthLeads`, `radiantExperienceLeads`, `players{steamAccountId, heroId, isRadiant, playerSlot, kills, networth, stats{networthPerMinute, killEvents{time}}}`, `towerDeaths{time, npcId, isRadiant}`, `pickBans`.

**Три ограничения, проверенные на живом API** — спека до 27.08.2026 предполагала обратное:

- **`matches(ids:)` требует админского токена** («User is not an admin»), поэтому обещанной выборки пачками нет: матчи качаются поштучно.
- **`playbackData` на бесплатном токене пуст.** И `buildingEvents`, и `roshanEvents` приходят пустыми массивами. Строения поэтому читаются из `towerDeaths` по таблице `npcId`.
- **Рошана и аегиса в STRATZ нет вовсе.** `roshanEvents` пуст, в `chatEvents` таких событий не нашлось (сопоставление 60 матчей — уровень случайности). Это и вывело три рошановских признака из вектора (§6.1).

**Разделение ролей:** поминутные ряды и строения — из STRATZ. OpenDota остаётся источником сводок `/proMatches`: принадлежность карты к серии знает только он (§4.2), и она не перезаписывается разбором деталей.

### 2.4 Источник C — Steam Web API (live)

**База:** `https://api.steampowered.com`, ключ бесплатно на `steamcommunity.com/dev/apikey`.

Это **единственный бесплатный канал живого состояния игры**. Без него основной сценарий продукта не работает.

#### C1. `GET /IDOTA2Match_570/GetLiveLeagueGames/v1/`

Список идущих турнирных матчей. Опрос каждые **20–30 секунд**.

Ключевые поля:
- `match_id`, `lobby_id`
- `league_id`, `league_node_id`
- `radiant_team{team_id, team_name, team_logo}`, `dire_team{...}`
- `radiant_series_wins`, `dire_series_wins`, `series_type` — счёт в серии
- **`stream_delay_s`** — задержка трансляции; важно для UI, см. §7.4
- `scoreboard{duration, roshan_respawn_timer, radiant{score, tower_state, barracks_state, picks, bans, players[]}, dire{...}}`
- `players[]` — заявленные составы с `account_id` и `hero_id`

> **Проверено на живом API 26.08.2026: `server_steam_id` в ответе отсутствует.**
> Замер по 37 идущим турнирным играм: поле не пришло ни в одной (`radiant_team` — в 21 из 37,
> остальные поля — во всех 37). `lobby_id` не является заменой: `GetRealtimeStats` с ним
> отвечает `400 Bad Request`. Значит, **связка C1 → C2 в описанном виде не работает.**
>
> Практические следствия:
> 1. **`scoreboard` из C1 самодостаточен для live-признаков.** По игроку приходят
>    `net_worth`, `gold`, `level`, `xp_per_min`, `gold_per_min`, `kills`/`death`/`assists`,
>    `last_hits`, `denies`, `hero_id`, `account_id`. По команде — `score`, `tower_state`,
>    `barracks_state`, `picks`, `bans`; по игре — `duration` и `roshan_respawn_timer`.
> 2. **`tower_state` и `barracks_state` — битовые маски того же формата, что
>    `tower_status_radiant` / `barracks_status_radiant` у OpenDota.** Это упрощает
>    train/serve parity по строениям, а не усложняет: обе стороны декодируются одним кодом.
> 3. Чего в C1 нет по сравнению с C2: поминутного ряда `graph_gold`, координат игроков и
>    точного `game_state`. Для признаков из §6.1 это некритично — `gold_adv` считается
>    суммированием `net_worth` по командам.
> 4. `server_steam_id` доступен через `GET /IDOTA2Match_570/GetTopLiveGame/v1/?partner=0`
>    (проверено: 10/10 игр с полем, `GetRealtimeStats` по нему работает), но это топ игр по
>    MMR, а не турнирные матчи, — как источник по Tier 1 не годится.
>
> **Вывод: основным каналом live-состояния считать C1, а не C2.** C2 использовать
> оппортунистически, если `server_steam_id` удастся получить.

#### C2. `GET /IDOTA2MatchStats_570/GetRealtimeStats/v1/?server_steam_id={id}`

Детальное состояние конкретной игры. Опрос каждые **10–20 секунд** по каждому активному `server_steam_id`.

- `match{server_steam_id, matchid, timestamp, game_time, game_state}`
- `teams[]{team_number, team_id, score, net_worth, players[]}`
  - `players[]{accountid, heroid, level, kill_count, death_count, assists_count, denies_count, lh_count, gold, net_worth, x, y, items[], abilities[]}`
- `buildings[]{team, type, lane, tier, destroyed, x, y}` — **точное состояние строений**
- `graph_data{graph_gold}` — ряд преимущества по золоту

**Признаки, изоморфные обучающим, даёт C1 (см. врезку выше), а C2 — только когда доступен
`server_steam_id`.** Соответствие полей train ↔ serve обязано быть покрыто тестами (см. §6.4).

#### C3. Вспомогательные

- `GET /IDOTA2Match_570/GetLeagueListing/v1/` — список лиг
- `GET /IDOTA2Match_570/GetMatchDetails/v1/?match_id=` — итоги матча (фолбэк, если OpenDota отстаёт)

### 2.5 Источник D — Liquipedia

Единственный авторитетный источник разметки **Tier 1** и расписания будущих матчей.

Два канала доступа:
1. **MediaWiki API** — `https://liquipedia.net/dota2/api.php` (`action=query`, `action=parse`). Работает без ключа.
2. **LPDB API** — структурированная база (турниры, матчи, команды, составы, размещения). Требует API-ключ по заявке. Формат и условия доступа стоит уточнить перед стартом — они менялись.

**Условия использования соблюдать строго:**
- кастомный `User-Agent` с названием проекта и контактным email
- rate limit ~1 запрос / 2 сек, для `parse` — ~1 / 30 сек
- обязательное кэширование ответов на своей стороне
- атрибуция CC-BY-SA на всех страницах, где данные отображаются

Нарушение = бан по IP. Опрос расписания — не чаще раза в час, всё остальное берётся из кэша.

Что забираем: `tier`, название и слаг турнира, даты, призовой фонд, организатор, LAN/online, список участников, ростеры на момент турнира, сетка и расписание матчей.

## 3. Разметка Tier 1

Автоматически вывести тир из данных нельзя. Процедура:

1. Забрать с Liquipedia список турниров с тегом Tier 1 за нужный период (~20–40 турниров в год).
2. Сопоставить каждый с `league_id` из OpenDota/Steam по названию + датам + призовому фонду. Матчинг **полуручной**: fuzzy-скоринг, спорные случаи — на ручное подтверждение. Объём делает это посильным.
3. Результат — таблица `leagues` с полями `steam_league_id`, `liquipedia_slug`, `tier`, `is_lan`, `prize_pool`, `organizer`, `region`, `start_date`, `end_date`.
4. Маппинг **версионируется**: турнир может быть переклассифицирован, история решений должна сохраняться.

Fallback до готовности маппинга — `tier == "premium"` из `/leagues` OpenDota.

## 4. Хранилище: модель данных

### 4.1 Слой сырых данных

| Таблица | Назначение |
|---|---|
| `raw_matches` | `match_id`, `source`, `fetched_at`, `payload JSONB` — полный ответ API как есть |
| `raw_live_snapshots` | `match_id`, `server_steam_id` (nullable, см. врезку в §2.4/C1), `captured_at`, `payload JSONB` — сырые ответы GetLiveLeagueGames / GetRealtimeStats |
| `raw_liquipedia` | `slug`, `fetched_at`, `payload JSONB` |

**Принцип: сырьё храним целиком и навсегда.** Фичи будут переразбираться десятки раз, перекачивать данные при этом недопустимо (квоты, время, риск исчезновения источника).

### 4.2 Нормализованный слой

| Таблица | Ключевые поля |
|---|---|
| `leagues` | `league_id`, `liquipedia_slug`, `tier`, `is_lan`, `prize_pool`, `region`, даты |
| `teams` | `team_id`, `name`, `tag`, `logo_url` |
| `players` | `account_id`, `name`, `country`, `fantasy_role` |
| `team_rosters` | `team_id`, `account_id`, `valid_from`, `valid_to`, `is_standin` — история составов |
| `matches` | `match_id`, `league_id`, `series_id`, `series_type`, `game_in_series`, `radiant_team_id`, `dire_team_id`, `radiant_win`, `start_time`, `duration`, `is_parsed`, `patch` |
| `match_players` | `match_id`, `account_id`, `hero_id`, `is_radiant`, `lane_role`, итоговая статистика |
| `match_drafts` | `match_id`, `order`, `is_pick`, `hero_id`, `team` |
| `match_objectives` | `match_id`, `time`, `type`, `team`, `key` |
| `series` | `series_id`, `league_id`, `stage_id`, `team_a`, `team_b`, `format` (`bo1`/`bo2`/`bo3`/`bo5`), `score_a`, `score_b`, `winner_team_id` **(NULLABLE)**, `is_draw BOOLEAN`, `scheduled_at` |
| `tournament_stages` | `stage_id`, `league_id`, `name`, `stage_type` (`group`/`playoff`/`swiss`), `default_format`, `points_rule` — источник истины по формату серий |

### 4.3 Слой обучающих данных

| Таблица | Назначение |
|---|---|
| `match_snapshots` | **Ядро датасета live-модели.** Одна строка = `(match_id, minute)` + все признаки состояния + лейбл `radiant_win` |
| `player_ratings` | `account_id`, `as_of_match_id`, `as_of_time`, `mu`, `sigma`, `games` — рейтинги **на момент каждого матча** |
| `team_features` | `team_id`, `as_of_time`, форма, Elo, статистика — точечно во времени |
| `predictions` | `match_id`, `minute`, `predicted_at`, `model_version`, `p_radiant`, `features JSONB` — лог всех выданных прогнозов |

Таблица `predictions` не опциональна: без неё через месяц невозможно понять, почему качество упало.

### 4.4 Правила целостности

- Все ingestion-операции **идемпотентны** (upsert по естественным ключам). Перезапуск воркера не должен порождать дубликаты.
- Прогресс бэкфилла хранится в чекпойнт-таблице (`source`, `cursor`, `updated_at`).
- Ретраи с экспоненциальным бэкоффом; 429 обрабатывается отдельно с уважением к `Retry-After`.
- Все временные метки — UTC.

## 5. Формирование датасета

### 5.1 Live-датасет (основной)

**Единица наблюдения:** снапшот `(match_id, minute)`. Один матч длительностью 40 минут → ~40 строк.

**Источник:** распарсенные матчи OpenDota. Ряды `radiant_gold_adv[]`, `radiant_xp_adv[]`, поигроковые `gold_t[]`, `xp_t[]`, `lh_t[]` + лог `objectives[]` разворачиваются в состояние на каждую минуту.

**Объём:** при 3 годах про-истории и ~60k карт всех тиров — порядка **2 млн строк**. Достаточно для градиентного бустинга с запасом.

**Лейбл:** `radiant_win` матча, продублированный на все снапшоты.

**Критично:** снапшоты одного матча сильно коррелированы. Любой сплит — только **по `match_id`**, никогда не по строкам.

### 5.2 Pre-match датасет

**Единица наблюдения:** карта. Все признаки рассчитаны строго **на момент `start_time`**, без единого байта информации из будущего.

**Объём:** ~60k карт за 3 года (все тиры), из них Tier 1 — ~3–4k.

### 5.3 Фильтрация (только по метаданным, известным до матча)

Отсекаем:
- лиги, отсутствующие на Liquipedia
- лиги с нулевым/неизвестным призовым, без организатора, созданные менее чем за неделю до старта
- матчи, где у команды нет `team_id` или ростер пуст
- матчи с 3+ стендинами (при этом `n_standins` сохраняем как признак)
- матчи с игроками, у которых менее 20–30 про-игр в истории
- `duration < 12 минут`, форфиты, матчи с `leaver_status != 0`

**Категорически не фильтруем по исходу.** Соблазн выкинуть «подозрительные сливы» приводит к модели, которая не знает о камбэках и систематически переоценивает лидера — ровно там, где на Tier 1 интереснее всего.

### 5.4 Веса тиров

Обучение идёт на всём про-сегменте, целевой домен — Tier 1:

```
tier 1: 1.0   tier 2: 0.6   tier 3: 0.3
× экспоненциальное затухание по возрасту патча
```

Альтернатива (предпочтительная): предобучение на всём корпусе + **калибровка на Tier 1**. Калибровка на целевом домене дешевле возни с весами и обычно эффективнее.

`tier` также подаётся отдельным признаком; на инференсе всегда подставляется значение 1.

### 5.5 Форматы серий, Bo2 и ничьи

#### Что затрагивает Bo2, а что нет

**Не затрагивает совсем:** live-модель и pre-match модель на уровне карты. Единица прогноза — карта, у карты всегда есть победитель. Bo2 — это просто две карты. Ядро продукта работает без изменений.

**Затрагивает:** всё, что живёт на уровне серии — таблица `series`, отображение счёта в UI, турнирные таблицы и модель вероятности серии (v2).

#### Определение формата

`series_type` из Steam/OpenDota ненадёжен (§2.2/A1). Источник истины — **Liquipedia**: формат задаётся стадией турнира (`group stage — Bo2`, `playoff — Bo3`, `grand final — Bo5`). Поэтому:

1. При синхронизации турнира с Liquipedia заполняем `tournament_stages` с `default_format`.
2. Каждую серию привязываем к стадии → формат берётся оттуда.
3. `series_type` из Valve — только для сверки и для случаев, когда стадия не размечена.
4. Отдельные серии могут отклоняться от формата стадии (переигровки, тай-брейки) — поле `format` хранится на самой серии, а не только на стадии.

#### Модель исхода серии (v2)

Для Bo1/Bo3/Bo5 исход бинарный. Для **Bo2 исход трёхзначный**: `2–0`, `1–1`, `0–2`. Соответственно:

- Не бинарная классификация, а **мультиномиальная** — три взаимоисключающих исхода.
- Наивная свёртка из вероятности карты: при `p` = вероятность победы команды A на карте, `P(2–0) = p²`, `P(1–1) = 2p(1−p)`, `P(0–2) = (1−p)²`. Это отправная точка, но **предположение независимости карт неверно** — вторая карта коррелирует с первой (подстройка драфта, психологический импульс, вскрытая информация о стратегии соперника). Корреляцию нужно оценить эмпирически и заложить поправку; на практике реальная доля исходов 1–1 обычно **выше** наивного `2p(1−p)`.
- В UI для Bo2 отображаются три вероятности, а не две.

#### Турнирные очки

Начисление за Bo2 зависит от регламента турнира (типичная схема DPC: 3 очка за 2–0, по 1 за 1–1, 0 за 0–2, но встречаются и другие). Правило хранится в `tournament_stages.points_rule` как конфигурация, **не хардкодится**.

#### Побочный аналитический эффект: Bo2 чище Bo3

Тонкий, но полезный момент. В Bo3 третья карта играется **только при счёте 1–1**, то есть выборка третьих карт смещена в сторону равных по силе противостояний. Признак «номер карты в серии» в Bo3/Bo5 несёт в себе эту селекцию и легко вводит модель в заблуждение.

В Bo2 вторая карта играется **всегда**, независимо от результата первой. Никакого отбора. Это делает Bo2 идеальным материалом для честной оценки эффекта «второй карты» (насколько результат первой карты влияет на вторую) — оценку затем можно переносить на Bo3/Bo5 с поправкой.

**Практический вывод:** признак `game_in_series` подавать не в сыром виде, а вместе с `series_format` и `is_conditional_game` (флаг «эта карта игралась только из-за счёта»), иначе модель выучит артефакт формата вместо реального эффекта.

#### Прочие форматы для полноты

- **Bo1** в групповых стадиях — ничьих нет, но и информации о серии тоже.
- **Bo3 с преимуществом** (одна команда стартует с 1–0) — редко, но встречается на некоторых турнирах.
- **Dead rubber** — карта, ничего не решающая. Мотивация команд падает, качество прогноза тоже. Флаг `is_dead_rubber` в бэклог; в Bo2 такого нет по определению, что ещё один аргумент в пользу его «чистоты».

## 6. ML-признаки

### 6.1 Live-признаки (состояние игры)

| Группа | Признаки |
|---|---|
| Время | `minute`, `log(minute+1)` |
| Экономика | `gold_adv`, `xp_adv`, нормированные `gold_adv/(t+5)`, дельта за последние 5 мин |
| Строения | живые башни по линиям и тирам, казармы, счёт по строениям, разница |
| Бой | разница килов, разница нетворса топ-кора, разброс нетворса внутри команды |
| Драфт | априорная оценка от драфт-подмодели (§6.3) |
| Prior | предматчевая вероятность от pre-match модели |
| Контекст | сторона Radiant (историческое преимущество ~52–55%), тир, LAN/online, `series_format`, `game_in_series`, `is_conditional_game`, счёт в серии (§5.5) |

**Рошан в вектор не входит** (решено 27.08.2026). Причина та же, что у `xp_adv` (§6.4):
live-канал `GetLiveLeagueGames` не передаёт ни числа убийств рошана, ни владельца аегиса —
оба признака были константами на проде, пока обучение видело настоящие значения. Время до
респауна табло отдаёт, но STRATZ, единственный источник поминутных рядов для обучения, не
отдаёт рошановских событий вовсе: `roshanEvents` приходит пустым, в `chatEvents` таких
записей нет (замерено на 60 матчах). Все три поля остаются в `GameState` как сырьё.

### 6.2 Pre-match признаки

- **Рейтинги на уровне игроков** (TrueSkill/Glicko по `account_id`), агрегированные в командный с учётом неопределённости. Это принципиально: команда как организация — фикция при шаффлах, пять конкретных аккаунтов с историей — нет.
- Форма: результаты за последние N матчей с временным затуханием
- Head-to-head за последние 6 месяцев
- Дни отдыха между матчами, число карт за последние 24 часа
- Патч, регион, LAN/online, стадия турнира (групповой / плей-офф / элиминация)
- `n_standins`, доля игроков, впервые играющих за эту команду

### 6.3 Драфт-подмодель

Отдельная модель `P(win | 10 героев + баны)`. Варианты по возрастанию сложности: матрица winrate/синергии/контрпиков → факторизация → эмбеддинги героев. Её выход — один признак в основных моделях.

### 6.4 Единый код признаков (train/serve parity)

Расчёт признаков живёт в **одном модуле**, используемом и оффлайн-пайплайном (из OpenDota), и live-сервисом (из Steam GetRealtimeStats). Поля источников различаются, поэтому:

- каждый источник имеет адаптер в общую промежуточную структуру `GameState`
- на каждый адаптер — тесты с зафиксированными эталонными матчами
- регрессионный тест: для завершённого матча признаки, собранные из live-снапшотов, должны совпадать с признаками, собранными из OpenDota-парсинга, в пределах допуска

Без этого train/serve skew гарантирован.

## 7. Валидация и метрики

### 7.1 Схема валидации

- **Только walk-forward по времени.** Обучение на патчах до N, тест на N+1. Случайный сплит запрещён.
- Группировка по `match_id` для live-датасета.
- Отдельный «замороженный» холдаут последних 2–3 месяцев, который не трогается при подборе гиперпараметров.

### 7.2 Метрики

Основные — **log loss** и **Brier score**, не accuracy. Обязательно **по срезам минут** (5 / 10 / 15 / 20 / 25 / 30+): усреднённая цифра врёт, поскольку на 40-й минуте задача тривиальна.

Дополнительно: reliability diagram, ECE, accuracy по срезам.

### 7.3 Бейзлайны

Модель обязана превосходить:
1. Константа 50%
2. Radiant-байас (историческая доля побед Radiant)
3. Логистическая регрессия на `gold_adv` и `minute` — удивительно сильный бейзлайн; если бустинг не бьёт его заметно, значит где-то баг
4. Pre-match Elo-фаворит (для pre-match модели)

### 7.4 Задержка трансляции

Steam API отдаёт состояние почти в реальном времени, зритель видит игру с задержкой (`stream_delay_s`, обычно 2–5 минут). Для UI это преимущество, но требует явного обозначения на интерфейсе, иначе пользователь решит, что модель «спойлерит». Опция «синхронизировать с трансляцией» (буферизация прогнозов на `stream_delay_s`) — в бэклог.

## 11. Дорожная карта

| Фаза | Длительность | Результат | Критерий готовности |
|---|---|---|---|
| **0. Скелет** | 2–3 дня | репозиторий, compose, FastAPI `/health`, React-заглушка | `docker compose up` поднимает всё одной командой |
| **1. Данные** | 1–2 нед | ingestion-воркеры, схема БД, бэкфилл 2–3 лет | в БД ≥ 40k про-матчей с игроками; перезапуск не даёт дубликатов |
| **2. Разметка** | 3–5 дней | маппинг Liquipedia ↔ league_id, таблица тиров | все Tier 1 турниры за 3 года размечены |
| **3. Фичи** | 1 нед | `match_snapshots`, рейтинги игроков point-in-time | ~2 млн снапшотов; тест на отсутствие утечек проходит |
| **4. Модель** | 1 нед | live-модель + калибровка, отчёт по метрикам | бьёт бейзлайн-логрегрессию на холдауте по log loss на всех срезах минут |
| **5. Live-петля** | 1 нед | поллер, инференс, WS, лог `predictions` | прогноз по идущему матчу обновляется каждые 30 сек |
| **6. Frontend** | 1–2 нед | F1–F6 | сценарий «открыл сайт → вижу идущий матч с графиком» работает |
| **7. Эксплуатация** | постоянно | переобучение по патчам, мониторинг дрейфа | алерт при росте ECE выше порога |

Порядок принципиален. Фазы 1–3 не дают ничего эффектного, и велик соблазн прыгнуть сразу к модели. Но модель на кривых данных переделывается трижды, а данные собираются один раз.

## 12. Риски и ограничения

| Риск | Влияние | Митигация |
|---|---|---|
| Утечка данных из будущего в признаки | фантастические метрики, провал в проде | point-in-time расчёт всего; отдельный тест-набор на утечки |
| Train/serve skew (OpenDota ↔ Steam) | модель в проде хуже, чем в ноутбуке | общий модуль признаков + регрессионные тесты (§6.4) |
| Дрейф патчей | деградация каждые 2–3 месяца | временное затухание весов, переобучение по расписанию, мониторинг калибровки |
| Изменение/закрытие внешних API | остановка сбора | хранение сырья, два независимых источника истории (A и B), абстракция за адаптерами |
| Исчерпание квот | простой бэкфилла | учёт квот в воркере, распределение нагрузки между A и B, кэш |
| Мало Tier 1 данных | переобучение | обучение на всём про-сегменте + калибровка на Tier 1 |
| Формат серии не определяется по данным Valve (Bo2 неотличим от двух Bo1) | неверный счёт серии в UI, поломанные турнирные таблицы, артефакт в признаке `game_in_series` | формат берётся из Liquipedia через `tournament_stages`; `winner_team_id` nullable + `is_draw`; тест «серий с 3 картами в Bo2 не существует» |
| Ростерные изменения в последний час | pre-match прогноз про «другую команду» | рейтинги на уровне игроков, проверка фактического состава из GetLiveLeagueGames |
| Блокировка Liquipedia | потеря разметки тиров | строгое соблюдение rate limit, агрессивный кэш, fallback на `tier=premium` из OpenDota |

## 13. Юридические и этические ограничения

- **Liquipedia:** CC-BY-SA — обязательная видимая атрибуция на страницах с их данными; соблюдение rate limit и требований к User-Agent.
- **Steam Web API:** данные Valve; Dota 2 — торговая марка Valve Corporation. Нужен дисклеймер об отсутствии аффилиации.
- **STRATZ / OpenDota:** соблюдение их ToS, атрибуция источника.
- **Персональные данные:** используются публичные игровые идентификаторы (`account_id`, никнеймы). Никаких попыток деанонимизации.
- **Позиционирование:** сервис аналитический. Если появится любая связь со ставками — возникает регуляторный вопрос, различающийся по юрисдикциям. В v1 этой связи нет и заводить её не следует без отдельной юридической проработки.
