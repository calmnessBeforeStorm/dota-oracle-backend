# Авторизация и панель запуска команд — дизайн

Дата: 2026-09-11. Статус: согласован по секциям, ждёт вычитки.
Затрагивает оба репозитория; источник истины — этот документ, план фронтенда ссылается на него.

## Зачем

Наполнение прод-базы сейчас делается руками: `docker compose run … python -m app.ingestion.cli <команда>`
по SSH, по одной строке. Это медленно и уже дважды ломалось на самой механике терминала —
вставленные пачкой команды съедал stdin контейнера, а `scp` запускался не на той машине.

Цель — дать **одному** пользователю, созданному скриптом на проде, кнопки в интерфейсе, которые
запускают те же команды и показывают их результат. Авторизация берётся по образцу из другого проекта
владельца (Argon2, короткий access-токен в памяти, refresh в httpOnly cookie с ротацией и детектом
повторного использования, синхронизация выхода между вкладками) с двумя осознанными отступлениями,
описанными ниже.

## Решения, принятые при согласовании

| Вопрос | Решение | Почему |
|---|---|---|
| Что запускают кнопки | **Только команды данных** | Обучение на проде бессмысленно: `featurize` строит выборку только из payload STRATZ (`app/features/featurize.py`), а STRATZ сервер блокирует. Промоушен из интерфейса потребовал бы доступа к Docker изнутри веб-приложения. |
| Как виден результат | **Журнал запусков** с выводом, дописываемым по ходу | `backfill` идёт ~13 минут, `map-leagues` — порядка получаса; «запустил и забыл» скрывает падения. |
| Цепочка | **Отдельные кнопки + «Наполнить по порядку»** | Первичное наполнение — восемь команд в строгом порядке. |
| Сессии | **Несколько устройств** — таблица сессий | Отступление от образца, где сессия одна (`users.session_id`). |
| Где выполняются команды | **Задачи arq в существующем воркере** | Долгая команда не занимает процесс, отдающий сайт; история переживает рестарты. |

Все признаки остаются: `prematch` и `featurize` в панели есть, хотя на проде сейчас дают мало —
`featurize` читает только STRATZ, а `prematch` нужны полные составы из деталей матчей.

## 1. Авторизация (бэкенд)

### Таблицы

**`users`**

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | UUID, PK | |
| `username` | text, unique, not null | |
| `display_name` | text, not null | |
| `password_hash` | text, not null | Argon2id |
| `permissions` | text[], not null | коды прав, см. ниже |
| `is_active` | bool, not null, default true | |
| `created_at`, `updated_at` | timestamptz | `TimestampMixin` |

**`auth_sessions`** — строка на устройство.

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | UUID, PK | попадает в refresh-токен как `sid` |
| `user_id` | UUID, FK → users, on delete cascade | |
| `token_hash` | text, not null | SHA-256 (hex) **текущего** refresh-токена |
| `created_at` | timestamptz | |
| `last_used_at` | timestamptz | |
| `expires_at` | timestamptz | |
| `revoked_at` | timestamptz, null | не null — сессия отозвана |

### Токены

Подпись HS256 ключом `SECRET_KEY`. Подписаны, но не зашифрованы: пароля и секретов внутри нет.

**access** — живёт **15 минут**, приходит в теле ответа.

| claim | значение |
|---|---|
| `sub` | `users.id` |
| `username` | логин |
| `display_name` | имя для шапки |
| `permissions` | полный список кодов прав |
| `token_type` | `"access"` |
| `exp` | срок |

**refresh** — живёт **7 дней**, приходит в cookie.

| claim | значение |
|---|---|
| `sub` | `users.id` |
| `sid` | `auth_sessions.id` |
| `jti` | случайный идентификатор, чтобы два токена одной сессии никогда не совпали |
| `token_type` | `"refresh"` |
| `exp` | срок |

`sid` — отступление от образца, нужное для нескольких устройств.

### Ротация и детект кражи

На `POST /refresh`:

1. Проверить подпись, срок и `token_type == "refresh"`. Иначе `401`.
2. Найти сессию по `sid`. Нет, отозвана (`revoked_at` не null) или истекла — `401`, cookie очищается.
3. Если SHA-256 предъявленного токена **равен** `token_hash` — выдать новую пару, записать в строку
   хеш нового refresh-токена, обновить `last_used_at`.
4. Если подпись верна, сессия жива, но хеш **не равен** текущему — предъявлен уже использованный токен.
   Отозвать **все** сессии пользователя, очистить cookie, `401`, записать в лог событие
   `auth.refresh_reuse` с `user_id` и IP.

### Эндпоинты `/api/auth`

Без `/v1` — как всё остальное API проекта.

| Метод | Путь | Вход | Результат |
|---|---|---|---|
| POST | `/login` | JSON `{username, password}` | `200 {access_token, token_type: "bearer", expires_in, user}` + Set-Cookie |
| POST | `/refresh` | cookie | `200` — та же форма, новая cookie |
| POST | `/logout` | cookie | `204`, сессия отозвана, cookie очищена |
| GET | `/me` | Bearer | `200 {id, username, display_name, permissions}` |

Неверный логин и неверный пароль дают **одинаковый** `401` с одним текстом. Для несуществующего
пользователя пароль всё равно проверяется против фиктивного Argon2-хеша, чтобы время ответа не
выдавало, существует ли логин.

### Cookie

`refresh_token`: `HttpOnly`, `SameSite=Strict`, `Path=/api/auth`, `Max-Age` = 7 дней,
`Secure` — только при `APP_ENV=production`. Локально на `http://localhost` cookie с `Secure`
браузер не принял бы.

`Strict` вместо `Lax` из образца: SPA и API на одном origin (Caddy на проде, dev-прокси Vite
локально), поэтому Strict ничего не ломает и полностью закрывает межсайтовую отправку cookie.

### Блокировка входа

Счётчики в Redis с TTL:

| Ключ | Порог | Окно | Блокировка |
|---|---|---|---|
| по логину | 5 неудач | 15 минут | 15 минут |
| по IP | 20 неудач | 15 минут | 15 минут |

Успешный вход сбрасывает счётчик логина. На заблокированный вход — `429` с заголовком `Retry-After`
в секундах; пароль при этом не проверяется.

IP берётся из `X-Forwarded-For`, которому uvicorn доверяет от любого адреса (`--forwarded-allow-ips '*'`
в `Dockerfile.prod`). Это безопасно **только потому**, что порт API наружу не опубликован и до него
доходит один Caddy. Об этом нужно написать комментарий у настройки: открытие порта превратит
блокировку по IP в фикцию, а сама настройка этого не покажет.

### Права

Проверяются по access-токену, без запроса к базе — как в образце. Зависимость
`require_permission(code)`: нет или невалидный токен — `401`, нет кода в `permissions` — `403`.
Следствие, принятое сознательно: отозванное право — и отозванная сессия, включая выход и
`revoke-sessions` — перестаёт действовать не сразу, а в течение 15 минут, пока не истечёт уже
выданный access-токен. Refresh после отзыва не пройдёт.

Коды:

| Код | Даёт |
|---|---|
| `pipeline.runs.view` | реестр команд и журнал запусков |
| `pipeline.run.<команда>` | запуск конкретной команды, например `pipeline.run.backfill` |
| `pipeline.run.chain` | запуск цепочки |

### Скрипт управления пользователем

`python -m app.auth.cli`:

| Подкоманда | Действие |
|---|---|
| `create-user --username U --display-name N` | создать пользователя со **всеми** известными правами |
| `set-password --username U` | сменить пароль и отозвать все сессии |
| `revoke-sessions --username U` | отозвать все сессии — на случай утечки |
| `grant-all --username U` | выдать все права, известные реестру сейчас |

`create-user` выдаёт права, существующие на момент создания. Когда в реестр добавляется команда,
её код у пользователя не появится сам — кнопка останется скрытой. Для этого `grant-all`; он же
печатает, какие коды добавил.

Пароль спрашивается через `getpass` **дважды** и никогда не передаётся аргументом: иначе он остался
бы в истории shell и в списке процессов.

На проде запускать **без `-T` и без `</dev/null`** — `getpass` нужен терминал:

```bash
docker compose -f docker-compose.prod.yml run --rm api \
  python -m app.auth.cli create-user --username adilet --display-name "Адилет"
```

### `SECRET_KEY`

Новая настройка `secret_key`. При `APP_ENV=production` приложение **отказывается стартовать**,
если ключ пуст или короче 32 байт: иначе токены подписывались бы значением по умолчанию из
публичного репозитория. В `deploy/env.prod.example` — с подсказкой `openssl rand -base64 48`.

## 2. Запуск команд (бэкенд)

### Реестр команд

Один модуль описывает каждую команду: имя, заголовок, описание, модель параметров (pydantic),
код права, список разрушительных флагов и функцию выполнения. Это единственный источник, из которого
строятся `GET /api/pipeline/commands` и проверка запроса на запуск.

| Команда | Параметры (как флаги CLI) | Разрушительные |
|---|---|---|
| `reference` | — | |
| `backfill` | `pages: int = 1`, `restart: bool = False` | `restart` |
| `catch-up` | `max_pages: int = 20` | |
| `normalize` | `limit: int \| None = None` | |
| `details` | `source: "stratz" \| "opendota" = "stratz"`, `limit: int = 100`, `oldest_first: bool = False` | |
| `resolve-outcomes` | `limit: int = 200` | |
| `map-leagues` | `limit: int \| None`, `apply: bool = False`, `active_days: int \| None`, `escalate: int = 0` | |
| `refresh-meta` | — | |
| `refresh-stages` | `limit: int \| None = None` | |
| `link-stages` | — | |
| `prematch` | — | |
| `featurize` | `limit: int \| None = None`, `rebuild: bool = False` | `rebuild` |
| `status` | — | |

Не входит `liquipedia <page>`: это отладочный просмотр страницы, а не наполнение.

Для `details` допустимые значения `source` сужаются до `opendota`, пока `STRATZ_AVAILABLE=false`:
`GET /commands` отдаёт только этот вариант и он же выбран по умолчанию в форме, а `POST /runs` со
`source=stratz` отвечает `422`. Вариант, который гарантированно упадёт с 403, не предлагается. Модель
параметров при этом хранит значение по умолчанию как в CLI (`stratz`) — сужение живёт слоем выше
и тест паритета не затрагивает.

**Паритет с CLI держит тест**: поля моделей параметров сверяются с флагами argparse в
`app/ingestion/cli.py` — имена, типы, значения по умолчанию. Кнопка и терминал не должны расходиться
молча.

Функции `cmd_*` в CLI получают параметр `out` (текстовый поток). CLI передаёт `sys.stdout`,
задача — буфер запуска. Логика команд не меняется, меняется адресат `print`.

### Таблица `pipeline_runs`

| Колонка | Тип | Примечание |
|---|---|---|
| `id` | UUID, PK | |
| `command` | text, not null | имя команды или `chain` |
| `params` | jsonb, not null | провалидированные параметры |
| `status` | text, not null | см. ниже |
| `created_by` | UUID, FK → users | кто запустил |
| `parent_id` | UUID, FK → pipeline_runs, on delete cascade, null | для шагов цепочки |
| `step_index` | int, null | порядок шага в цепочке |
| `output` | text, not null, default `''` | вывод, хвост не больше 1 МБ |
| `error` | text, null | текст исключения |
| `created_at` | timestamptz | |
| `started_at`, `finished_at` | timestamptz, null | |

Статусы: `queued` → `running` → `succeeded` \| `failed`; также `interrupted` (воркер умер во время
выполнения) и `skipped` (шаг цепочки после упавшего).

**Один запуск за раз** — частичный уникальный индекс по верхнеуровневым активным записям:
`UNIQUE ((true)) WHERE status IN ('queued', 'running') AND parent_id IS NULL`. Цепочка считается одним
запуском. Гарантия на уровне базы, а не проверкой в коде: два быстрых клика не проскочат гонкой.

Хранятся последние **200** верхнеуровневых запусков. Более старые **завершённые** удаляются при
создании нового, шаги уходят каскадом; активный запуск не удаляется никогда.

### Эндпоинты `/api/pipeline`

| Метод | Путь | Право | Результат |
|---|---|---|---|
| GET | `/commands` | `pipeline.runs.view` | реестр: имена, заголовки, схемы параметров, разрушительные флаги |
| POST | `/runs` | `pipeline.run.<команда>` или `pipeline.run.chain` | `202` с записью запуска |
| GET | `/runs` | `pipeline.runs.view` | последние запуски без вывода |
| GET | `/runs/{id}` | `pipeline.runs.view` | запуск с выводом и шагами |

Тело `POST /runs`: `{command, params, confirm}`. Порядок проверок:

1. токен и право на эту команду — `401` / `403`;
2. параметры — `422`;
3. разрушительный флаг без `confirm: true` — `400`. Подтверждение только в интерфейсе не защищает
   от запроса мимо интерфейса;
4. есть активный запуск — `409`, в теле — текущий активный запуск. Гонка двух запросов, которую
   проверка не поймала, упирается в уникальный индекс: `IntegrityError` при вставке тоже превращается
   в `409`;
5. создать `queued`, поставить задачу arq, `202`.

API держит пул arq, созданный в жизненном цикле приложения. Сейчас API в arq ничего не ставит — пул
появляется впервые.

### Выполнение в воркере

Задача `run_pipeline_command(run_id)`:

1. Атомарно перевести запись из `queued` в `running` (`UPDATE … WHERE status = 'queued'`). Если строка
   не обновилась — выйти: запуск уже взят или отменён.
2. Выставить `contextvar` с `run_id`, выполнить функцию команды с `out` = буфер запуска.
3. Буфер сбрасывается в `output` раз в **2 секунды** и в конце. При превышении 1 МБ хранится хвост.
4. Успех — `succeeded`; исключение — `failed` и текст в `error`. `finished_at` ставится в обоих случаях.

Таймаут задачи — **2 часа**.

**Логи в журнал.** На корневой логгер вешается обработчик, который пропускает запись в буфер только
если `contextvar` текущего контекста равен `run_id`. `contextvars` наследуются asyncio-задачами,
поэтому логи, возникшие внутри команды, попадают в её журнал, а логи поллера и кронов, идущих
в том же процессе, — нет. Перехватывать `sys.stdout` целиком нельзя именно из-за них.

**Цепочка** — одна задача, шаги создаются сразу, все в статусе `queued`, чтобы в журнале был виден
весь план:

| # | Команда | Параметры |
|---|---|---|
| 0 | `reference` | — |
| 1 | `backfill` | `pages=400` |
| 2 | `normalize` | — |
| 3 | `map-leagues` | `apply=true`, `active_days=800`, `escalate=6` |
| 4 | `refresh-stages` | — |
| 5 | `link-stages` | — |
| 6 | `prematch` | — |
| 7 | `featurize` | — |

Шаги выполняются по порядку. Первый упавший останавливает цепочку, оставшиеся получают `skipped`,
сама цепочка — `failed`. Иначе `featurize` отработал бы поверх недонаполненных таблиц.

**Рестарт воркера** (деплой, падение). При старте воркер:

- переводит записи в `running` — и верхнего уровня, и шаги — в `interrupted`;
- шагам цепочки, которые остались `queued` под прерванной цепочкой, ставит `skipped`: их выполняла
  та же умершая задача, и больше их никто не возьмёт;
- верхнеуровневые `queued` не трогает: их задача лежит в Redis и выполнится после рестарта.

Задача регистрируется с `max_tries=1`, чтобы arq не перезапустил прерванную команду сам. Даже если
перезапуск случится, первый пункт выполнения — атомарный перевод из `queued` — не даст выполнить
запуск повторно, потому что статус уже `interrupted`.

### Известные оговорки

- Кроны продолжают работать параллельно с ручными запусками: `normalize` в `:52` может совпасть
  с ручным `backfill`. С CLI происходит то же самое сейчас, это не новый риск.
- `status` быстрый, но тоже идёт через очередь — одна модель запуска для всех команд проще, чем
  две.

## 3. Фронтенд

### Хранение access-токена

Только в памяти вкладки — модульный стор на `useSyncExternalStore`. Zustand не добавляется: ради
одного значения в проекте, где его нет, новая зависимость не нужна. В `localStorage` и
`sessionStorage` токен не попадает — это закрепляется тестом.

Рядом с токеном хранятся разобранные claims (`username`, `display_name`, `permissions`, `exp`).
Разбор — base64url-декодирование payload без проверки подписи: подпись проверяет сервер, клиенту
claims нужны только для отображения и скрытия кнопок.

### AuthInitializer

При старте приложения вызывает `POST /api/auth/refresh`. Успех — токен в стор; `401` — пользователь
анонимный. Публичные страницы **не ждут** ответа; ожидание состояния инициализации есть только у
`/admin`.

### Клиент API

- Если токен есть, подставляется `Authorization: Bearer …`.
- На `401` — одно обновление пары и один повтор запроса.
- Обновление **общее** (single-flight): одновременные запросы с истёкшим токеном ждут одного
  `refresh`. Иначе второй запрос предъявил бы уже использованный refresh-токен, сработал бы детектор
  кражи и отозвал бы сессии на всех устройствах.
- Если обновление не удалось — стор очищается, в канал уходит `logout`.

### Синхронизация вкладок

`BroadcastChannel("dota-oracle-auth")`, сообщения `login` и `logout`. Токен по каналу не передаётся:
на `login` соседняя вкладка сама вызывает `refresh`. Если `BroadcastChannel` недоступен —
синхронизация просто не происходит, вход работает.

### Маршруты

**`/login`** — логин и пароль. На `401` — одно сообщение без подробностей. На `429` — «попробуйте
через N минут» по `Retry-After`. После входа — переход на `next` или `/admin`.

**`/admin`** — панель. Анонимного пользователя перенаправляет на `/login?next=/admin`. Пункт «Панель»
в навигации виден только после входа; ссылки на вход в публичной шапке нет, `/login` открывается по
прямому адресу.

### Панель

- **Команды.** Форма каждой строится из `GET /api/pipeline/commands`: `int` — числовое поле,
  `bool` — переключатель, выбор — список; значения по умолчанию как в CLI. Разрушительный флаг
  открывает подтверждение и отправляет `confirm: true`. Кнопка видна, только если право есть в
  токене; проверяет всё равно сервер — скрытие кнопки удобство, а не защита.
- **Цепочка.** Кнопка «Наполнить по порядку» со списком шагов и их параметрами.
- **Журнал.** Статусы, длительность, раскрывающийся моноширинный вывод с прокруткой к концу. Пока
  есть активный запуск, журнал опрашивается раз в 2 секунды; в покое — нет. `409` при запуске
  показывает, что сейчас выполняется.
- **Шапка панели.** Имя пользователя и «Выйти»: `POST /api/auth/logout`, очистка стора, `logout`
  в канал.

Визуально — существующие токены и примитивы редизайна (`Surface`, `Pending`) в плотной раскладке.

## 4. Выкатка, безопасность, ошибки, тесты

### Зависимости и окружение

- Бэкенд: `argon2-cffi`, `PyJWT`. Фронтенд — ничего нового.
- `SECRET_KEY` в `.env` прода. Миграция создаёт `users`, `auth_sessions`, `pipeline_runs` и
  накатывается `deploy.sh` автоматически.
- Caddy не меняется: origin один, cookie с `Path=/api/auth` проходит через прокси как есть.

### Безопасность

- Эндпоинты запуска принимают только `Bearer` в заголовке, не cookie, поэтому межсайтовая подделка
  запроса к ним невозможна. Cookie используется только `/refresh` и `/logout`: `POST`,
  `SameSite=Strict`, `Path=/api/auth`.
- Токены и пароль не логируются никогда. Вход логируется: логин, IP, успех или неудача.
- `pipeline_runs.created_by` фиксирует, кто запустил команду.

### Коды ошибок

| Код | Когда |
|---|---|
| `400` | разрушительный флаг без `confirm` |
| `401` | нет токена, истёк, неверный тип; неверный логин или пароль |
| `403` | нет права |
| `409` | уже есть активный запуск |
| `422` | параметры не прошли валидацию |
| `429` | вход заблокирован; с `Retry-After` |

### Тесты бэкенда

Только на тестовой схеме — никогда на боевой базе (инвариант проекта после истории с
`run_normalize`).

- Хеширование и проверка пароля; фиктивная проверка для несуществующего логина.
- Токены: срок, подпись, тип; access не принимается как refresh и наоборот.
- Ротация: новый хеш в строке сессии после `refresh`.
- **Повторное предъявление использованного refresh-токена отзывает все сессии пользователя.**
- Отозванная и истёкшая сессия — `401`.
- Блокировка: порог по логину, порог по IP, `Retry-After`, сброс счётчика при успешном входе.
- `require_permission`: `401` без токена, `403` без кода.
- `SECRET_KEY`: отказ стартовать в production с пустым или коротким ключом.
- Реестр команд совпадает с флагами argparse.
- Жизненный цикл запуска: `queued → running → succeeded`, `failed` с текстом ошибки.
- `409` при активном запуске, включая гонку двух вставок против уникального индекса.
- `400` для разрушительного флага без подтверждения.
- Цепочка: остановка на упавшем шаге, `skipped` у остальных, `failed` у цепочки.
- `interrupted` для `running` при старте воркера; `queued` не трогается.
- **Логи параллельной задачи не попадают в журнал чужого запуска.**
- Обрезка вывода по хвосту при превышении 1 МБ.
- Хранение не больше 200 верхнеуровневых запусков.

### Тесты фронтенда

- Токен не попадает в `localStorage` и `sessionStorage`.
- Два одновременных `401` вызывают один `refresh`; запрос повторяется после обновления.
- Неудачный `refresh` очищает стор и отправляет `logout` в канал.
- `/login`: сообщение на `401`, сообщение с минутами на `429`.
- `/admin` перенаправляет анонимного пользователя на `/login?next=/admin`.
- Видны только кнопки, на которые есть право.
- Разрушительный флаг требует подтверждения и отправляет `confirm: true`.
- Журнал опрашивается только пока есть активный запуск.

### Проверка на проде после выката

1. `SECRET_KEY` в `.env`, `./deploy.sh`.
2. Создать пользователя командой из раздела 1.
3. Войти на `/login`, открыть `/admin`.
4. Запустить `status`, увидеть вывод в журнале.

### Вне объёма

Обучение и промоушен модели, регистрация, управление ролями из интерфейса, восстановление пароля
по почте, двухфакторный вход, отмена идущего запуска.
