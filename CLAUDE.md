# CLAUDE.md — dota-oracle-backend

Бэкенд системы прогнозирования исходов профессиональных матчей Dota 2.
Полная спецификация: [docs/spec.md](docs/spec.md) — **читай её перед любой содержательной задачей**,
ссылки вида «§5.5» ниже указывают на её разделы.

## Что это

Сервис в реальном времени оценивает вероятность победы каждой команды в идущих матчах
Tier 1 и отдаёт турнирный календарь. Две разные ML-задачи, смешивать их нельзя:

| | Pre-match | **Live (основная)** |
|---|---|---|
| Когда | до старта карты | каждые 20–30 сек по ходу игры |
| Роль в v1 | вспомогательная, даёт prior | **основной продукт** |

Единица прогноза — **карта**, у неё всегда есть победитель. Серия — отдельный уровень (§5.5).

## Текущее состояние

Сводка для передачи сессии — раздел «Текущий шаг» в `../CLAUDE.md`: что работает по фазам,
цифры в БД, главный блокер и варианты решения. Ниже — детали этой кодовой базы.

**Фазы 1–3 и 5** по дорожной карте §11, идут сейчас.

- Фаза 0 закрыта: compose поднимает всё одной командой, `/health` отвечает.
- Схема БД в миграциях, 18 таблиц.
- Бэкфилл `/proMatches` → `raw_matches` работает, идемпотентен, резюмируется по чекпойнту.
  **Он ходит только назад.** Матчи, сыгранные после его старта, подбирает отдельный
  догоняющий проход `catch-up` (свой чекпойнт `opendota_pro_matches_newest`, стоит на cron
  раз в час). Без него выборка заканчивается днём старта бэкфилла, и ни один прогноз
  live-петли невозможно сверить с исходом — замерено: все 212 предсказанных матчей лежали
  выше самого свежего матча в базе.
- Нормализация сырья → `leagues` / `teams` / `series` / `matches` работает, включая
  нумерацию карт в серии и счёт серии со сменой сторон.
- **Нормализация стоит на cron** (`normalize_stored_payloads`, :52). Это было единственное
  звено цепочки без расписания, и обрыв не выглядел ошибкой: `resolve-outcomes` клал
  STRATZ-payload в `raw_matches`, все джобы рапортовали успех, а дашборд точности оставался
  пуст, потому что исход из payload читает только `normalize`. Замерено 28.08.2026: у
  80 матчей версии `0.2` payload лежал по 50, а `matches.radiant_win` — тоже по 50, и
  только после ручного прогона. **Прогон полный, без курсора** — идемпотентен (инвариант 5),
  но дорожает с архивом. Замерено 01.09.2026 на живом кроне: **61–65 секунд** на 28 595
  сводочных payload и 6001 детальный, то есть «около двух минут» было пессимизмом и курсор
  по `raw_matches` пока не нужен. Слот переехал с :47 на **:52**: худший случай резолвера —
  `OUTCOMES_PER_RUN` карт на троттле, 400 секунд, и старое :47 лежало внутри него.
- **Выборка тоже на cron** (`refresh_training_set`, 04:05 UTC) — последнее звено, которое
  двигалось только руками. `prematch` и `featurize` идут **одной джобой и в этом порядке**:
  `featurize` подставляет prior 0.5 и пустой pre-match блок карте, у которой нет
  pre-match строки, поэтому расписание для одного `featurize` тихо заливало бы дефолты в те
  же колонки, где рядом лежат измеренные значения — ровно тот дефект, что был у `is_lan`.
  Truncate на cron не понадобился: у `featurize` нет курсора, обычный проход и так
  переписывает всю таблицу, а `--rebuild` нужен, только чтобы **убрать** строки, которых
  текущий набор признаков больше не породит. Замер: `prematch` 11 с, `featurize` 42 с.
- Детали матчей (`/matches/{id}`) грузятся и разбираются в `match_players`,
  `match_drafts`, `match_objectives`; `matches.patch` заполняется оттуда же.
- **Фаза 2 начата:** форматы серий читаются со страниц Liquipedia (`{{Abbr/BoN}}` в
  секции `== Format ==`), лиги сопоставляются с турнирами скорингом по имени, решения
  версионируются в `league_mappings`.
- **Закачка деталей идёт сама.** `backfill_details_hourly` на cron берёт `DETAILS_PER_HOUR`
  карт в час (300) и на этом останавливается. Бюджет намеренно ниже квоты: её же делит
  `resolve_prediction_outcomes`, а прогноз, который некому сверить, не учит ничему. Замерено
  28.08.2026 — безлимитный прогон отрубило на 476 картах, то есть весь часовой запас
  выгребает тот, кто стартовал первым. **Перепроверено 01.09.2026 и подтверждено:** прогон на
  1200 карт отрубило на **557 за 20 минут** с `Retry-After: 648s`. Потолок STRATZ — порядка
  550–650 карт в час на всех потребителей, а не 2000 из таблицы лимитов ниже; поднимать
  `DETAILS_PER_HOUR` некуда. Обрыв отработал как задумано: прогон остановился, а не пошёл
  добивать список по отказу в секунду.
  **Полтора месяца эта джоба качала половину заявленного.** У arq дефолтный `job_timeout`
  300 секунд, а 300 карт при троттле STRATZ 2 с/карту требуют 600: прогон брал ровно 150
  карт и падал на 299.98 s с голым `TimeoutError`, каждый час. Замерено 01.09.2026 — строки
  ложатся по **30 в минуту** пять минут подряд, это троттл, а не совпадение. Таймауты обеих
  STRATZ-джоб теперь **выводятся** из `StratzClient.min_interval` (`stratz_slice_timeout`),
  а не записаны числом: числу нечем сказать, что бюджет поменяли.
- **Воркер не умел жаловаться, а логи умели болтать.** Два дефекта наблюдаемости, найденных
  01.09.2026 и починенных вместе. Healthcheck воркера унаследован из образа API и делал
  `curl localhost:8000/api/health` — процесс arq не отдаёт HTTP вовсе, так что контейнер
  писал `unhealthy` с первой секунды жизни и всегда: лампа, горящая красным постоянно, не
  несёт информации и закрывает собой настоящую. Теперь проверяется живая запись arq в Redis
  (`arq ... --check`), `health_check_interval = 30`, TTL записи на секунду больше.
  Второе: `STEAM_API_KEY` печатался в `docker compose logs` целиком дважды в минуту — httpx
  логирует URL запроса **сам**, на INFO, а `redact()` применялся только там, где строку
  собираем мы. Фильтр теперь стоит на корневом хендлере (`app/core/logging.py`), а не на
  логгере по имени: следующая библиотека будет не httpx. **Фильтр обязан чистить
  отрендеренную запись, а не аргументы по одному** — httpx передаёт `request.url` объектом
  `httpx.URL`, и проверка `isinstance(arg, str)` пропускает ровно тот аргумент, в котором
  лежит ключ. Первая версия так и прошла собственные тесты, продолжая течь на живом воркере.
- Серии привязываются к стадиям по датам (`link-stages`), оттуда получают `format`,
  победителя/ничью и флаг `is_conditional_game`. **1814 серий из 13 667** после прогона
  разметки с эскалацией 28.08.2026 (было 434). Из привязки: 1506 попали в одну стадию,
  175 — в несколько согласных, 17 разрешены по числу карт; 74 остались неоднозначными
  (стадии перекрываются и спорят о формате), 138 не покрыты ни одной стадией.
- Сопоставление лиг: **32 Tier 1, 7 Tier 2, 22 Tier 3, 156 без тира** из 217. Эскалация по
  составам решает случаи, где имя слабое, а корроборация полная — `SLAM IV` → `BLAST/SLAM/4`
  при сходстве имени 0.68, но датах 1.00 и составах 1.00. Оставшиеся 136 — в основном
  квалификации и любительские лиги; часть кандидатов Liquipedia отдаёт не турнирной
  страницей, а статьёй об игроке, и такие правильно оставлять неразмеченными.
- **Bo2 в данных появился 28.08.2026.** 16 серий формата Bo2, из них **3 закончились 1–1**
  (`is_draw = true`, `winner_team_id = NULL`, две карты) — FISSURE Universe Episode 7.
  Механика §5.5 впервые прошла на реальных данных, а не только в тестах, и UI рисует
  «BO2 1 : 1 (ничья)» правильно. До этого весь путь ничьи существовал на фикстурах.
- **Фаза 3 начата:** состояние строений разворачивается по минутам из `objectives`,
  `match_snapshots` строятся (`featurize`), тест на утечки проходит.
- Pre-match признаки (`prematch`) считаются одной хронологической развёрткой: рейтинги
  TrueSkill по `account_id`, винрейты героев, форма команд с затуханием, личные встречи.
  Всё, что записано на матч, — состояние **до** него.
- В векторе снапшота **28 признаков**, включая `prematch_prior` и 8 pre-match разниц.
  Рошана нет — `GetLiveLeagueGames` не отдаёт ни числа убийств, ни владельца аегиса, а STRATZ
  не отдаёт рошановских событий вовсе (инвариант 2). `tier` выведен 28.08.2026:
  замерено, что он был константой `1.0` во всех 3974 матчах, и это не просто бесполезность,
  а ловушка — §5.4 фиксирует его в 1 на инференсе, поэтому меняющийся в обучении тир и есть
  train/serve skew по построению.
- **Неизвестное в векторе помечается отдельной колонкой.** Вектор из float не умеет сказать
  «не знаю», поэтому `is_lan` и формат серии идут парами: `is_lan` + `is_lan_known`,
  `series_len` + `series_format_known`. Без этого отсутствующий факт и настоящий делят одно
  число, и модель учит наше покрытие разметкой, а не игру. Замерено на `is_conditional_game`:
  у серий с известным форматом решающих карт **19.4%**, у залитых — **0.1%**, потому что в
  Bo1 одна карта. То есть без флага этот признак означает не «карта решающая», а «карта
  решающая **и** её лигу мы сопоставили». Покрытие на 28.08.2026: место известно у 31.3%
  снапшотов (13.4% LAN), формат — у 18.4%.
- **Валидация режется по `start_time`, а не по патчу — сознательное отступление от §7.1.**
  Спека требует «обучение на патчах до N, тест на N+1». `matches.patch` у STRATZ-карт
  остаётся NULL (`gameVersionId` — другая шкала), то есть у подавляющего большинства карт
  патча просто нет, и схема в написанном виде неисполнима. Разница невелика: патчи выходят
  раз в несколько недель, а `split_by_time` режет хронологически по матчам. Вернуться к
  патчам можно, когда появится способ сопоставить `gameVersionId` со шкалой OpenDota.
- **Ещё нет:** синергий и контрпиков в драфте (§6.3 предполагает развитие до факторизации),
  моделей фаз 4–5.
- **В проде обученная модель с 01.09.2026** — `lgbm-20260901-090724`: log loss 0.5253,
  brier 0.1778, ECE 0.0201 на холдауте в 1226 матчей. Активируется `ACTIVE_MODEL_VERSION`;
  промоушен остаётся ручным, потому что модель, промоутящая себя сама, однажды промоутит
  регрессию. Провалов гейта было 6 при холдауте 795, 4 при 881, 3 при 907, 1 при 1120 и 0
  при 1226 — история гейта здесь целиком история размера выборки, ни один признак ради этого
  не менялся. Калибратор впервые настоящий: `platt` вместо `identity`.
- **У гейта есть порог шума, выведенный бутстрэпом** (`app/ml/significance.py`). Сравнение
  парное — обе модели считаются на одних строках, — поэтому разницу ресэмплим напрямую,
  **по матчам, не по строкам** (инвариант 3: построчный бутстрэп даёт интервал в разы уже, и
  именно поэтому 0.0012 выглядел приговором). Три вердикта: `better` / `tied` / `worse`; гейт
  валит только `worse`, ничьи печатаются громко и пишутся в карточку. Ресэмплинг **посеян**:
  гейт, отвечающий по-разному при перезапуске, хуже отсутствующего.
  Отдаваемая модель проходит гейт с **3 ничьими из 21 сравнения**: в корзинах 15–19, 20–24 и
  25–29 она от `logistic-gold-minute` неотличима (−0.0044 ± 0.0058, −0.0013 ± 0.0059,
  −0.0047 ± 0.0063). Измеримо лучше — рано (0–4: −0.0190 ± 0.0076) и поздно (30+: −0.0195 ±
  0.0104). Проход есть, запаса в середине игры нет.
- **Промоушен не работал ни одним из четырёх способов, и это выяснилось только когда его
  впервые попробовали.** Калибратор фитился и выбрасывался (в карточке было только имя, а
  `LightGBMPredictor` грузил голый бустер — отдавалась бы функция, которую никто не
  оценивал); у воркера, который и делает живые прогнозы, вообще не было каталога `models`;
  lightgbm лежал в extra `ml`, так что **ни один serving-образ не мог прочитать артефакт**
  (`model.load_failed: No module named 'lightgbm'`); и venv на хосте отставал на ту же
  зависимость. Любые два из этих четырёх дали бы **две разные модели под одним номером
  версии** — API одну, воркер другую. Теперь коэффициенты калибровки лежат в карточке и
  применяются на инференсе, `./models` смонтирован в оба serving-контейнера read-only, а
  lightgbm — основная зависимость (scikit-learn остался в extra: обучение это не выдача).
- **Петля обратной связи замкнута:** `resolve-outcomes` спрашивает у STRATZ исход именно тех
  матчей, по которым мы уже отдали прогноз, и `/api/model/metrics` считает по ним калибровку
  (F6). Ждать, пока до них дойдёт сводочный поток, не работает — замерено 28.08.2026: верх
  `/proMatches` совпадал с самым свежим матчем в базе и не двигался десять часов, а над ним
  висело 220 предсказанных матчей.

Критерий выхода из фазы 1 (§11): ≥ 40k про-матчей с игроками, перезапуск не даёт дубликатов.
**Половина выполнена 01.09.2026:** 55 654 матча, история с 2024-08-25 — 400 страниц
`/proMatches` дали 40 000 матчей за 13 минут без единого 429. Суточная квота OpenDota бьёт по
`/matches/{id}`, где один вызов это одна карта; сводочный эндпойнт отдаёт сотню за вызов,
поэтому вся глубина стоила 400 вызовов. **«С игроками» не выполнено:** детальный разбор есть
у 7046 карт, в очереди 48 308, это ~161 час работы воркера.

**§5.3 реализована в `app/features/eligibility.py`, и не буквально.** Из семи фильтров
применимы четыре (длительность, ростер, `team_id`, абандон), три отброшены как фильтры по
нашему покрытию, а не по качеству матча: `organizer` пуст у 96% лиг, `prize_pool` у 75%,
лига не сопоставлена с Liquipedia у 71% — все три поля **заполняются** сопоставлением, поэтому
«нет организатора» значит «лигу не размечали». Главное: **абандон это `leaverStatus >= 2`, а
не `!= 0`**. Единственное ненулевое значение во всём архиве — `1` (DISCONNECTED), реконнект,
рутинный в про-игре; значений `2` и хуже нет ни одного, а буквальное «!= 0» удалило бы 2132
карты из 6129. Стендины посчитать нечем (`is_standin` захардкожен в `False`), фильтр по числу
про-игр отложен: `match_players` покрывает только скачанные карты, поэтому он удалял бы 60–70%
каждого месяца, рассказывая про бэкфилл, а не про игроков.

**§5.4 реализована в `app/ml/pipeline.py`, работает предпочтительная схема.**
`calibration_rows` фитит калибратор на Tier 1, когда его хватает по `MIN_CALIBRATION_MATCHES`,
иначе на всей валидации, и пишет в карточку, что именно произошло — переключится само
(сейчас Tier 1 в валидации 192 при пороге 500). `tier_weights` даёт §5.4-веса с затуханием по
возрасту (полураспад 180 дней вместо патча, как и в §7.1), **включены по умолчанию по
замеру**: лучше в трёх поздних корзинах, ничья в четырёх ранних, хуже нигде. Замер сделан на
холдауте — один бит из него утёк, это записано в `TIER_WEIGHTS`. `tier` в вектор признаков
по-прежнему не входит (§5.4 фиксирует его в 1 на инференсе — это train/serve skew), а вот
взвешивать по нему можно: вес живёт только внутри обучения.

Модель по умолчанию — `BaselinePredictor` (логрегрессия на `gold_adv_norm` и `minute`),
родственник бейзлайна №3 из §7.3: настоящая модель обязана его заметно бить. Коэффициенты
не выдуманы, а посажены на 21 199 снапшотах из 491 матча и проверены на 140 более поздних.

**Одно и то же преимущество в золоте значит тем меньше, чем позже.** Замерено по 30 539
снапшотам: отрыв больше 8k даёт победу в 98.0% случаев на минутах 10–20 и в 82.9% после
сороковой; отставание меньше −8k отыгрывается в 6.1% случаев рано и в 13.5% поздно. Признак
`gold_adv_norm = gold_adv / (minute + GOLD_NORM_OFFSET)` в векторе был с самого начала — а
отдаваемая модель читала **сырой** `gold_adv`, да ещё с обратным знаком временнóго члена.
На холдауте это стоило log loss 0.8514 против 0.5377 и **1.299 в корзине «30+», то есть хуже
монетки (0.693)**. Accuracy при этом почти не менялась (0.727 против 0.732) — ровно тот
случай, ради которого §7.2 запрещает судить по ней.

**Дрейф калибровки — сравнение, а не порог.** `app/ml/drift.py` сравнивает последние 7 дней
прогнозов одной версии с её же более ранними и **выводит порог из размера окна**, а не берёт
константу. Замерено на нашем логе (200 случайных разбиений одной модели пополам): p90
расхождения ECE между половинами — 0.077 при 85 матчах на сторону, 0.098 при 50, 0.135 при 25.
Отсюда `noise_floor(n) = 0.077 · √(85/n)`; предсказывает 0.100 и 0.142 для 50 и 25 — совпадает
с замером, хотя подгонялось только по одной точке. Константа была бы неверна дважды: сегодня
она пропускает шум, а через месяц данных глохнет. Абсолютный порог не работает в принципе —
бейзлайн стоит на ECE ≈ 0.056 постоянно, и любой уровень либо не срабатывает никогда, либо
срабатывает всегда. Окна считаются **в матчах** (§5.1). Проверка руками:
`docker compose run --rm tools python -m app.ml.cli drift`.

**Наружу никогда не уходит уверенность.** `get_predictor()` оборачивает любую модель в
`_Bounded`, который зажимает вероятность в `SERVING_BOUNDS = (0.01, 0.99)`. Замерено по
нашему же логу прогнозов 28.08.2026: из 86 завершённых матчей, где бейзлайн заявлял ≥99.9%
за сторону, эта сторона проиграла 8 раз. Цена не только в доверии: бейзлайн зажимает логит
на ±20, поэтому уверенная ошибка стоит 20 нат против 0.5 у обычной строки — один камбэк
решал log loss всей корзины «30+» на дашборде. Это **страховка, а не калибровка**: честными
вероятности делает только обученная модель с калибровочным шагом (фаза 4). Обёртка живёт в
слое выдачи, а не внутри `BaselinePredictor`, чтобы правило пережило подмену модели.

Измерено на реальных данных: **41,4 про-матча в сутки, ≈ 15 100 в год**. Три года истории
укладываются в одну месячную квоту OpenDota по объёму, но **не по суточному лимиту**:
без API-ключа реальный прогон отрубается примерно на 700 матчах в день. Планировать надо
днями, а не часами. Скорость самих запросов тоже ниже расчётной — ~16,5 карт в минуту.
`RateLimitedError` обрабатывается отдельно от прочих ошибок: прогон **останавливается**,
а не продолжает долбить API — иначе это прямой путь к бану по IP. Два места, где это
правило уже ломалось, и оба чинились 28.08.2026: `post_json` (а постит только STRATZ —
источник всей обучающей выборки) не проверял 429 и не имел retry-политики, поэтому отказы
приходили обычными `HTTPStatusError`; а счётчик отказов в `details` срабатывал только если
не скачано **ничего**, так что прогон, начавшийся успешно и упёршийся в квоту, добивал
оставшиеся 1600 идентификаторов по одному отказу в две секунды и выходил с кодом 0.
Теперь лимит считает **подряд идущие** отказы и сбрасывается на каждом успехе.

## Инварианты — нарушать нельзя

1. **Никакой информации из будущего в признаках.** Всё считается point-in-time. Пример
   ловушки: `tower_status_radiant` в ответе OpenDota — это состояние на конец матча, в
   снапшот 15-й минуты его класть нельзя. Строения разворачиваются реплеем `building_kill`
   из `objectives` (`app/features/buildings.py`); тот же модуль декодирует live-битмаски,
   поэтому обе стороны считают строения одним кодом.
   Проверка — `tests/features/test_leakage.py`: признаки минуты N обязаны совпадать
   при расчёте по полному матчу и по матчу, обрезанному сразу после минуты N.
   **Этой проверки недостаточно, и это стоило нам целого датасета.** 27.08.2026 нашлась
   утечка, которую она не может поймать по построению: `series_wins_diff` нёс **итоговый**
   счёт серии, взятый из `series.score_a/score_b`. Карта из серии, закончившейся 2:0,
   заявляла «+2» уже на нулевой минуте — а это возможно, только если сторона выиграла
   именно эту карту. Замер по таблице: `series_wins_diff = +2` → Radiant побеждает в 100%
   случаев, `−2` → в 0.6%. Обученная модель угадывала исход на минуте 0 в 87.9% случаев.
   Тест на обрезание слеп к этому: он режет payload матча и заново гоняет адаптер, а
   контекст серии приходит не из payload, а из нормализованных таблиц, и в обоих прогонах
   одинаков. Счёт теперь восстанавливается из предыдущих карт серии
   (`featurize.contexts_for`), закреплено `tests/features/test_series_context_leak.py`.
   **Мораль: любой признак, приходящий не из payload матча, тест на обрезание не проверяет.
   Такие признаки проверять отдельно — например, сверкой с исходом на минуте 0.**
   Pre-match признаки — тот же принцип во времени: `rebuild_prematch` идёт по матчам в
   хронологическом порядке и на каждом делает ровно три шага в этом порядке — спросить
   накопители, записать строку, скормить им результат. Любой другой порядок, и матч
   предсказывает сам себя. Пересборка всегда полная: приход старого матча из бэкфилла
   обесценивает всё, что после него.
   **`prematch` запускать до `featurize`** — иначе снапшоты получат нулевой prior.
2. **Признаки считаются в одном месте** — `app/features/live.py`, из `GameState`. Все
   источники (STRATZ, OpenDota, Steam) приводятся к `GameState` адаптерами. Иначе train/serve skew
   гарантирован (§6.4). Новый признак → `FEATURE_ORDER` + билдер + оба адаптера + тест.
   **Признак существует только если его могут дать все источники.** Это правило стоило нам
   `xp_adv`: у OpenDota он точный, а из live-табло не восстанавливается — замерено на 400
   матчах, уровень по XP угадывается в 53% случаев, итоговая ошибка `xp_adv` 25.6%. Точно
   в обучении и на четверть мимо в проде — это и есть тот самый skew.
   Оно же 27.08.2026 стоило нам **рошана**: `GetLiveLeagueGames` не передаёт ни числа
   убийств, ни владельца аегиса — оба признака были константами на проде, — а STRATZ не
   отдаёт рошановских событий вовсе. Вектор с 30 признаков сократился до 27.
   **Разные источники могут считать разные величины под одним именем.** Поминутный ряд
   OpenDota (`gold_t`, `radiant_gold_adv`) — накопленное **добытое золото**; ряд STRATZ
   (`networthPerMinute`, `radiantNetworthLeads`) и live-табло — **net worth**. Расхождение
   678 в первые 70% матча и 2987 в последние 30%. Смешивать их в одной выборке нельзя,
   поэтому `featurize` читает **только** `stratz_match`.
3. **Любой сплит — по `match_id`**, никогда по строкам: снапшоты одного матча сильно
   коррелированы (§5.1). Валидация только walk-forward по времени.
   **Отсюда же правило отчётности:** 151 600 снапшотов — это сведения о 3 981 матче, а не
   о 151 600 независимых наблюдениях. Размер выборки называть в матчах; в строках он льстит
   ровно в число снапшотов на матч.
4. **Сырьё храним целиком и навсегда** (`raw_*`). Признаки будут переразбираться десятки
   раз, перекачивать данные нельзя — квоты, время, риск исчезновения источника.
5. **Все ingestion-операции идемпотентны** (upsert по естественным ключам), прогресс — в
   `ingest_checkpoints`. Перезапуск воркера не должен порождать дубликаты.
6. **Все временные метки — UTC.**
7. **Не фильтруем выборку по исходу.** Выкидывание «подозрительных сливов» даёт модель,
   которая не знает о камбэках (§5.3).
8. **Каждый выданный прогноз пишется в `predictions`** с `model_version` и `features`.
   Без этого падение качества через месяц необъяснимо.
9. **Имена команд — не идентификаторы.** Valve запрещает букмекерские названия на The
   International, поэтому PARIVISION играет как Vision, а BetBoom Team как BoomBoys;
   в наших данных это `TEAM VISION`, `PVISION`, `BoomBoys`, `Team Yandex`, причём
   `BoomBoys` встречается под **двумя разными `team_id`**. Сопоставление по составу это
   переживает (доля, а не равенство), но сверка одного имени — нет: расхождение по чемпиону
   не имеет права перебить согласный состав.
10. **`series_id` от Valve уникален только внутри лиги.** Идентичность серии —
   `(league_id, valve_series_id)`, в БД под суррогатным `series.series_id`. Замерено: при
   ключе по одному лишь Valve-идентификатору серии из разных лиг склеивались в одну.
   Значения `0` и `null` означают «серии нет» — это не идентификатор.
11. **`/matches/{id}` не знает о сериях.** `series_id` и `series_type` приходят оттуда
    `null` — принадлежность к серии владеет только слой сводок `/proMatches`, и разбор
    деталей не имеет права её перезаписывать.
12. **Дочерние строки матча заменяются, а не мерджатся.** `match_players`, `match_drafts`
    и `match_objectives` принадлежат тому разбору, который их породил. Upsert по
    `(match_id, ordinal)` выглядит эквивалентным и не является им: разбор, дающий **меньше**
    строк, обновит те, что покрыл, и оставит хвост. Ровно это и случилось — карта, разобранная
    из OpenDota (43 события), а потом из STRATZ (24), показывала каждое позднее событие
    дважды. `normalize._replace_children` сначала удаляет, потом вставляет.
13. **Детальный payload может создать матч, но только заполняя пробелы.** Обычный порядок —
    сводка, потом детали, и тогда `_ensure_matches` не делает ничего нового. Он нужен, когда
    сводка опаздывает или не приходит вовсе: без него матч, по которому live-петля уже отдала
    прогноз, невидим целиком — вместе с исходом, — а дочерние строки нельзя даже вставить,
    у них FK на `matches`. Правило записи — `coalesce(существующее, новое)` по каждой колонке:
    сводочный слой владеет этими полями, детальный разбор имеет право только дозаполнить.
    `league_id` в скелет не пишется (FK на `leagues`, которые населяет сводочный слой),
    `series_id` — тем более (инвариант 11).
14. **Неизвестное хранится как NULL, а не как значение по умолчанию.** `series.format` и
    `matches.is_conditional_game` остаются NULL до фазы 2: подстановка `bo3` неотличима от
    знания позже, а `is_conditional_game` идёт прямо в обучающую выборку.

## Серии, Bo2 и ничьи (§5.5) — источник частых ошибок

- `series_type` от Valve **ненадёжен**: Bo2 в нём не представлен (приходит `0`), и отличить
  Bo2 от двух независимых Bo1 по данным Steam/OpenDota невозможно.
- Источник истины по формату — **Liquipedia**, через `tournament_stages.default_format`.
  Сопоставление лиги со страницей — не только по имени: `prop=pageprops` отдаёт
  сгенерированное описание `metadescl` с датами, тиром, числом команд и призовым, и это
  дешёвый `query`-запрос вместо `parse` с лимитом 1/30 сек. Даты сверяются с окном наших
  матчей и работают в первую очередь как **вето**: непересекающиеся даты бракуют кандидата
  с любым сходством имени.
  Формат читается из секции `== Format ==` шаблонами `{{Abbr/BoN}}`; регистр шаблона плавает,
  исключения пишутся в одном предложении с правилом («Grand Final is Bo5, all other
  matches are Bo3»), поэтому решение принимается по фразе, а не по строке.
  Поле `format` дублируется на самой серии: тай-брейки и переигровки отклоняются от
  дефолта стадии. Порядок разрешения — в `app/domain/series.resolve_format()`.
- `series.winner_team_id` **nullable** + отдельный флаг `is_draw`. «Ещё не решено» и
  «ничья 1–1» — разные состояния, путать их в UI нельзя.
- Признак `game_in_series` подавать только вместе с `series_format` и
  `is_conditional_game`. В Bo3 третья карта играется лишь при 1–1, то есть выборка третьих
  карт смещена; без флага модель выучит артефакт формата.
- Начисление турнирных очков за Bo2 — конфигурация в `tournament_stages.points_rule`,
  **не хардкод**: регламенты разные.
- Вероятность исхода Bo2 — трёхзначная (2–0 / 1–1 / 0–2), мультиномиальная. Наивная свёртка
  `p²/2p(1−p)/(1−p)²` — только отправная точка: карты не независимы, реальная доля 1–1 выше.

## Live-источник: спека расходится с реальностью (проверено 26.08.2026)

Спека описывала связку C1 → C2: из `GetLiveLeagueGames` берём `server_steam_id`, по нему
дёргаем `GetRealtimeStats`. **На живом API это не работает.**

- `server_steam_id` не пришёл **ни в одной из 37** идущих турнирных игр.
- `lobby_id` не заменяет его: `GetRealtimeStats` отвечает `400 Bad Request`.
- `GetTopLiveGame` отдаёт `server_steam_id` (10/10), но это топ игр по MMR, а не Tier 1.

**Основной канал live-состояния — C1 (`GetLiveLeagueGames`), а не C2.** Его `scoreboard`
самодостаточен: по игроку — `net_worth`, `gold`, `level`, `xp_per_min`, `gold_per_min`,
`kills`/`death`/`assists`, `last_hits`, `denies`; по команде — `score`, `tower_state`,
`barracks_state`, `picks`, `bans`; по игре — `duration`, `roshan_respawn_timer`.

Два следствия для кода:

1. `tower_state` и `barracks_state` — **битовые маски того же формата, что
   `tower_status_radiant` / `barracks_status_radiant` у OpenDota**. Декодер писать один,
   общий для обоих адаптеров, — это прямой выигрыш для train/serve parity (§6.4).
2. `gold_adv` на live-стороне считается суммой `net_worth` по командам, а не из
   `graph_gold` (ряда в C1 нет). Расхождение с офлайн-расчётом обязано быть покрыто
   регрессионным тестом.

`raw_live_snapshots.server_steam_id` поэтому nullable, а `source` различает канал.

**Карточка идущего матча собирается из `raw_live_snapshots`.** Нормализованный слой про live-матч
не знает ничего: `match_players` и `match_drafts` строятся из детального payload, который
появляется только после конца игры. Раньше карточка честно отвечала «есть только кривая» и
показывала две безымянные стороны и 0:0 всё время, пока идёт матч. В payload поллера есть всё:
названия команд, счёт по убийствам, счёт серии, драфт и оба состава с героем, K/D/A, нетворсом,
GPM и XPM. Правило то же, что у детальных парсеров, — **дозаполнять, а не перезаписывать**:
как только матч нормализован, побеждает нормализованный слой (разбор реплея точнее табло,
снятого в середине боя). Счёт по убийствам живёт в `map_score` отдельной функцией: у
завершённого матча его надо брать из составов, потому что последний live-снапшот сделан за
полминуты до падения трона — замерено, 52:48 против 51:53 у одного и того же матча.

**Матч без `scoreboard` — не состояние игры.** `GetLiveLeagueGames` показывает матч с момента
сбора лобби, и до гонга у записи `scoreboard` нет вовсе (905 из 16303 сохранённых payload).
Все поля тогда падают в ноль, включая битовые маски строений, а ноль в них — это не
«неизвестно», а **все башни и все казармы разрушены**. Замерено: 84 из 86 матчей, по которым
есть обе половины, имели записанный прогноз на минуте 0, построенный ровно из этого.
`from_live_league_game` теперь отказывается строить состояние без табло, а поллер такие игры
пропускает (`drafting` в логе `live_poll.tick`). Записанные ранее строки остаются в
`predictions` — это честный след того, что мы отдавали, и переписывать его нельзя (инвариант 8).

**Train/serve parity (§6.4) больше не `skip`.** Замерено на 86 парных матчах, 3067 пар
минут: `gold_adv` — медиана расхождения 213, p90 1136 (это и подтверждает переход на STRATZ:
обе стороны считают net worth); строения совпадают точно в 81% минут и с точностью до одной
в 98%; убийства — самое слабое место, точно в 61%, потому что live-табло сообщает убийство
в момент события, а `killEvents` несёт время реплея. Фикстура из трёх реальных матчей —
`tests/fixtures/train_serve_pairs.json`.

**Лог `predictions` не стабилен по схеме.** В нём лежат строки всех наборов признаков,
которые когда-либо отдавались, — старые несут `roshan_kills`, `aegis_holder`,
`roshan_respawn_in`, — а `model_version` при сокращении вектора с 30 до 27 не менялся. Для
бейзлайна это безвредно (он читает `gold_adv` и `minute`), но знать это надо до того, как
`predictions.features` кто-нибудь прочитает как обучающие данные.

## Внешние источники и их лимиты (§2)

| Источник | Роль | Лимит, который реально бьёт |
|---|---|---|
| OpenDota | сводки `/proMatches`, принадлежность к серии | **суточный лимит бьёт первым**: без ключа прогон отрубило на 685 матчах, 429 без `Retry-After` |
| STRATZ | **поминутные ряды и строения** — из них строятся снапшоты | **~550–650 карт/час** замерено дважды, а не 2000 из документации |
| Steam | **live-состояние**, без него продукта нет | мягкие, ~100k/сут |
| Liquipedia | тиры, расписание, **форматы серий** | ~1 req/2 сек, `parse` ~1/30 сек |

Liquipedia банит по IP: кастомный `User-Agent` с контактом обязателен, кэш обязателен,
атрибуция CC-BY-SA на страницах с их данными обязательна (§13). Троттлинг зашит в
`app/ingestion/clients/base.py` — новые клиенты наследовать оттуда, а не писать httpx руками.

## Команды

**Разработка и прод — разные файлы и разные образы.**

**Однократная подготовка.** `requires-python` — строго `>=3.12,<3.13`, а на машине владельца
системный Python 3.14, где pip просто откажется ставить пакет. Поэтому нужен venv на 3.12;
интерпретатор ставится рядом с существующим, не вместо него:

```bash
winget install --id Python.Python.3.12    # если 3.12 ещё нет: py -0p покажет
py -3.12 -m venv .venv
.venv/Scripts/python.exe -m pip install -e ".[dev]"
cp .env.example .env                       # STEAM_API_KEY нужен для live-контура
```

**Каждый день — три терминала.**

```bash
# 1. хранилища и воркер
docker compose up -d

# 2. API
.venv/Scripts/python.exe -m uvicorn app.main:app --reload --port 8100

# 3. SPA
cd ../dota-oracle-frontend && npm run dev
```

Порты нестандартные: 8100 API, 5273 SPA, 5442 Postgres, 6389 Redis. Дев-сервер SPA
проксирует `/api` и `/ws` на 8100, так что открывать надо `localhost:5273`.

# Всё, что умеет образ API, кроме обслуживания запросов: тесты, ruff, mypy, alembic, CLI.
# `run --rm` поднимает контейнер на одну команду и выбрасывает.
docker compose run --rm tools python -m pytest
docker compose run --rm tools python -m app.ingestion.cli status

pip install -e ".[dev]"         # локально, Python 3.12
pytest                          # тесты (те, что с БД, скипнутся без неё)
ruff check . && ruff format .   # линт
mypy app                        # типы (strict)

# миграции создаются внутри контейнера — там Python 3.12 и asyncpg
docker compose run --rm tools alembic revision --autogenerate -m "описание"
docker compose run --rm tools alembic upgrade head

# наполнение БД
docker compose run --rm tools python -m app.ingestion.cli backfill --pages 50   # вглубь истории
docker compose run --rm tools python -m app.ingestion.cli catch-up             # свежие матчи
docker compose run --rm tools python -m app.ingestion.cli details --source stratz --limit 700
docker compose run --rm tools python -m app.ingestion.cli resolve-outcomes  # исходы под прогнозы
docker compose run --rm tools python -m app.ingestion.cli reference   # герои и имена игроков
docker compose run --rm tools python -m app.ingestion.cli normalize
docker compose run --rm tools python -m app.ingestion.cli status

# фаза 2: разметка тиров и форматов
docker compose run --rm tools python -m app.ingestion.cli map-leagues            # сухой прогон
docker compose run --rm tools python -m app.ingestion.cli map-leagues --apply    # применить уверенные
docker compose run --rm tools python -m app.ingestion.cli liquipedia "The International/2024"
```

**`alembic downgrade base` на рабочей БД не запускать.** Он дропает все таблицы вместе с
накопленным сырьём, а бэкфилл — это часы закачки и расход месячной квоты OpenDota. Проверку
отката гоняет CI на заведомо пустой базе; локально достаточно `upgrade head`. Если откат
действительно нужен — откатывать на одну ревизию (`alembic downgrade -1`), а не до нуля.

### Прод — один образ на всё

Фронт и бэкенд собираются в **один образ**: nginx раздаёт статику SPA и проксирует `/api` и
`/ws` на uvicorn в том же контейнере. Одним образом, а не двумя, — потому что SPA бесполезен
без ровно этого API, а API не публичный продукт: версионировать их порознь значит завести
матрицу совместимости, которую некому вести.

**Собирать из директории выше**, потому что фронтенд — соседний чекаут, а Docker не умеет
выходить за пределы своего контекста:

```bash
cd .. && docker compose -f dota-oracle-backend/docker-compose.prod.yml up -d --build
```

Два процесса в одном контейнере — плата за такую компоновку, и у неё одна настоящая
опасность: если uvicorn умрёт, nginx продолжит отдавать SPA, контейнер останется «здоровым»,
а весь `/api` будет отвечать 502. `deploy/entrypoint.sh` это закрывает — ни один из процессов
не переживает другого, контейнер падает, оркестратор перезапускает. Проверено: убийство
uvicorn роняет контейнер с кодом 1.

Healthcheck ходит **через nginx**, а не напрямую в uvicorn: так проверяется путь, которым
идёт посетитель, и сломанный прокси валит проверку, а не прячется за здоровым API.

Docs API: `http://localhost:8100/docs`.

## Правила ведения репозитория

Общие правила монорепо-пары описаны в `../CLAUDE.md`, коротко:

- Дефолтная ветка — **`development`** (тестовый сервер). Вся работа ветвится от неё.
- Каждая фича — отдельная ветка от `development`: `feature/<кратко>`, `fix/<кратко>`.
  Прямых коммитов в `development` нет, только мердж.
- **В `main` категорически нельзя коммитить и пушить.** Единственный путь кода в прод —
  мердж `development` → `main`, и он делается **только по явному разрешению владельца
  проекта на этот конкретный мердж**. Разрешение не переносится на следующие разы.
  По своей инициативе в `main` не ходить и не предлагать этого.
- Коммиты подписываются почтой **`ersaim.adilet@yandex.kz`** (в репозитории уже прописан
  локальный `user.email`, не перезаписывать глобальным).
- **Сообщения коммитов — на английском**, в императиве: `add live match poller`, а не
  `added changes`. Трейлеры об авторстве ИИ не добавляются.
- Перед пушем прогнать то же, что гоняет CI:
  `ruff check . && ruff format --check . && mypy app && pytest`.
  **Именно `.`, а не `app tests`** — CI проверяет весь репозиторий, и расхождение уже
  роняло пайплайн. `mypy` здесь в режиме `strict` — он ловит то, чего не видят тесты
  (например, вызовы неаннотированных функций из сторонних библиотек).
- **У CI нет `.env`.** Тест, которому нужен ключ, проходит локально и падает в пайплайне —
  так и случилось с тестами STRATZ-клиента: `StratzClient.__init__` отказывается
  существовать без токена. Ключи в CI класть незачем, тесты сеть не трогают, поэтому токен
  подставляется фикстурой. Проверять так:

  ```bash
  docker compose run --rm -e STRATZ_API_TOKEN= -e STEAM_API_KEY= tools python -m pytest
  ```
